# M6 — Coins and gifts

**Goal (PRD):** the ledger, screens 10 and 11, Apple and Google in-app purchases with
server-side receipt checks, and daily check-in. Covers MN-1 to MN-5 (MN-4 for the in-app
part only, see decision 4).
**Accept:** buying a pack in the store sandboxes credits exactly once even when the webhook
is sent again, and the balance always equals the sum of the ledger.

## 1. Ledger (MN-2)

- **`CoinLedger`** (PRD fields): user, delta (+/-), reason, ref_type, ref_id,
  idempotency_key (unique), created_at.
  - **Append-only**, enforced by a Postgres trigger that rejects UPDATE and DELETE (as for
    `ModerationAction` in M4).
  - Balance = `SUM(delta)`, never a stored number. Indexed on (user, created_at).
- **`wallet.post_entry(user, delta, reason, ref, idempotency_key)`** is the only writer:
  - **Idempotent.** The same key returns the existing entry. The same key with a different
    user or amount is an error, never a second write.
  - **No overdraft.** A per-user Postgres advisory lock serialises one user's writes, so two
    gifts sent at once can't both spend the last coins. A debit that would go below zero
    fails with `insufficient_coins`. The one exception is refunds (decision 5).
  - After commit, it sends `wallet.updated {balance, spent_today}` to the user's devices.
- **Reasons:** `purchase`, `purchase_bonus`, `gift`, `daily_checkin`, `invite_reward`,
  `refund`. M7 adds the pay-as-you-go reasons.
- **Endpoints:**
  - `GET wallet`: balance, spent_today (Lagos day). The daily cap arrives with M7.
  - `GET wallet/ledger`: paged, newest first (the store's History tab).
- **Reconciliation (Observability: "ledger mismatches"):** a nightly Celery job, also run as
  `manage.py check_ledger`. It checks that:
  - every verified purchase has exactly its credits
  - every gift has exactly one debit
  - no balance is negative except after a refund
  - Each finding is logged as an error and counted in a metric.

## 2. Coin packs and in-app purchases (MN-1, MN-4)

```
app ──buy (Google Play Billing / StoreKit 2)──► store
app ──POST purchases/verify {store, product_id, token or signed transaction}──► server
server ──check with the store──► credit with key purchase:<store>:<transaction id> ──► 200
app ──completes the purchase (consume) only after the 200
store ──webhook (Google RTDN / Apple notifications v2)──► server ──same key──► no second credit
```

- **Packs come from the server:** `GET wallet/packs` returns product id, coins, bonus and
  tag ("Popular", "Best value"). **Prices come from the store** (the localised ₦ price
  string), so the app never hard-codes a price.
  - 100 (Starter), 550 (+50 bonus), 1,200 (+200 bonus), 3,000 (+700 bonus). See decision 1.
- **`Purchase`** (PRD fields): store, product_id, txn_id (unique), amount_ngn, status,
  raw_receipt.
- **Google:**
  - The Play Developer API (`purchases.products.get`) checks the purchase token for the
    right package and product, and that it is paid.
  - The key is the order id. After crediting, the server acknowledges the purchase; the app
    then consumes it, so the pack can be bought again.
  - Real-time developer notifications (Pub/Sub push to `webhooks/google`) credit purchases
    the app never reported, for example when the app was killed mid-purchase, and revoke
    refunds (voided purchases).
- **Apple:**
  - The StoreKit 2 signed transaction is checked on the server with Apple's official
    `app-store-server-library`: signature chain to Apple's root, bundle id, product, and
    environment.
  - The key is the transaction id.
  - App Store Server Notifications v2 (`webhooks/apple`): `ONE_TIME_CHARGE` credits and
    `REFUND` revokes. Each notification's own signature is checked.
- **Behind interfaces with fakes:** `StoreVerifier` for Google and Apple. The fake accepts
  tokens shaped `fake:<product>:<txn>`, so the whole flow runs locally and in tests.
- **App:** the official `in_app_purchase` plugin. Purchases still pending when the app
  restarts are sent to `verify` again on launch, so nothing paid is ever lost.

## 3. Free coins (MN-3)

- **Daily check-in:** `POST wallet/claim-daily`.
  - +10 coins once per day. The day runs from midnight to midnight in Lagos time.
  - The streak counts days in a row; it goes 1 to 7, then starts again at 1. Missing a day
    resets it (decision 2).
  - The key is `checkin:<user>:<date>`, so a double tap or a retry never pays twice.
  - The store shows "Day N of 7 · +10 coins" with Claim, or "Claimed today".
- **Invite a friend:** +50 coins to the inviter when the invited person passes the selfie
  check.
  - Each user gets an invite code. "Share link" opens the phone's share sheet with a link
    carrying the code.
  - The code reaches the new install through the Play Install Referrer on Android, or an app
    link if the app is already installed. On iOS there is no install referrer (decision 3).
  - Abuse checks:
    - one reward per invited person
    - none if the invited person's device id was seen before (M4 device ids)
    - none for banned accounts
  - The key is `invite:<invited user>`.

## 4. Gifts (MN-5) — screen 11

- **`Gift`** (catalogue; edited in Django admin and seeded with the 8 PRD gifts at their
  prices) and **`GiftSend`**: sender, receiver, session or friendship, gift, ledger_entry.
- **`POST sessions/{id}/gifts {gift, idempotency_key}`** during a live session, and
  `POST chats/{id}/gifts` in a friend chat. The 06 design has the gift button, and friend
  chats use 06.
  - The service layer sets the price from the catalogue. The app only sends the gift slug and
    a key it generates once per tap, so a retry never charges twice.
  - Refused when the session has ended, either person has blocked the other, or coins are
    short.
  - It debits the sender; **the receiver gets nothing** (MN-5).
  - It writes a `gift` message into the chat ("Ada sent you a Jollof"), so it shows in the
    transcript and in saved friend history.
  - Both people get `gift.received {session_id or chat_id, gift, sender}`.
- **App:**
  - **Screen 11:** a sheet over the video call (04) or chat (06), with the 8 gifts, the
    balance and "Top up", "Back to call", and "Send · N coins". When coins are short the
    main button becomes "Top up coins" and opens the store.
  - **On send:** both people see the gift animation. The sender gets the design's "You sent
    Tobi a Jollof" toast; the receiver gets "Tobi sent you a Jollof".
  - The gift button returns to the video call controls and the chat composer. Voice calls
    (05) have no gift button in the design, so none is added.

## 5. Screen 10 — Coin store

- Balance, the 4 packs (selected card, tag and bonus as designed), and "Buy N coins". The
  price comes from the store.
- **Earn free coins:** check-in with streak, and invite with "Share link".
- **History tab** (no design): ledger rows with an icon per reason, the amount, and the date.
- Home's coin pill shows the live balance through `wallet.updated`; it shows 0 today.
- The footer line "Card, bank transfer or USSD" is left out until the web top-up is decided
  (decision 4). "Coins don’t expire" stays.

## Tests and acceptance

- **Backend unit tests (MN IDs in names):**
  - `post_entry`: idempotency, the same key with a different amount refused, no overdraft
    under concurrent debits (threads on a real database), append-only triggers
  - purchase verify, both stores with fakes: wrong product or package refused, pending not
    credited, the same transaction from verify and from the webhook credited once
  - refunds revoked
  - check-in day boundary and streak reset
  - invite reward once, and not for a reused device
  - gifts: price from the catalogue, ended session refused, blocked pair refused, the
    message written, the event sent
  - reconciliation catching a planted mismatch
- **Acceptance, live stack:**
  - An e2e test buys a pack through the fake store, sends the webhook three times in
    parallel, and then calls `verify` again. Pass: exactly one credit, and
    `GET wallet` equals the ledger sum. `check_ledger` then reports nothing.
  - Then two clients in a call: a gift is debited once and both get `gift.received`.
  - **Store sandboxes:** the same check with a real Play test purchase and an Apple sandbox
    purchase, once the store accounts exist (decision 6). The webhook replay uses the
    stores' own "send test notification", plus replaying the saved request.
- **App:** widget tests for 10 (pack selection, check-in states, History) and 11 (send, short
  balance, toast). The purchase flow runs against a fake purchase stream. Goldens of 10 and
  11 against the designs.

## Decisions to confirm

1. **What a pack gives.** The design shows "550" with "+50 bonus". **Recommendation:** the
   big number is the total you get (550 = 500 + 50 bonus). This matches MN-10, where auto
   top-up "buys 550 coins". It is written as two ledger rows, `purchase` 500 and
   `purchase_bonus` 50, so a refund or a later cash-out can tell paid coins from bonus coins.
   The packs are 100, 500+50, 1,000+200 and 2,300+700.
2. **Check-in streak.** +10 every day (the design shows a flat +10). After day 7 the streak
   starts again at 1; missing a day resets it. Days run midnight to midnight in Lagos.
   **No extra day-7 reward**, since the PRD gives none.
3. **Invites on iOS.** Android passes the code through the Play Install Referrer
   automatically. iOS has no equivalent, so either (a) iOS invites only count when the app
   is already installed and the link opens it, or (b) a small "Have an invite code?" field
   in onboarding (no design). **Recommendation: (a) for the MVP,** because Android is most of
   the market. Also: should rewards be capped (for example 20 a month per inviter) against
   farming? Not in the PRD; device-id and selfie checks are the guard for now.
4. **Web top-up with Paystack (card, bank transfer, USSD).** MN-4 says to check store rules
   first (questions #2). **Recommendation: not in M6.** Only in-app purchases, and the
   design's "Card, bank transfer or USSD" line is hidden until a store or legal review says
   yes. `webhooks/paystack` waits with it.
5. **Refund after the coins are spent.** A refunded pack is debited even if that takes the
   balance below zero. A negative balance blocks spending until topped up, and raises the
   account's risk score. **Recommendation: yes.** Otherwise "buy, gift, refund" is free
   coins.
6. **Store accounts.** The sandbox acceptance needs:
   - **Google:** a Play Console app on at least the internal test track, the 4 products, a
     service account with Play access, a Pub/Sub topic for notifications, and a licence
     tester account.
   - **Apple:** an App Store Connect app, the 4 products, an In-App Purchase key, and the
     notification URL.
   - Both webhooks need a public HTTPS address (a tunnel such as Cloudflare Tunnel in
     development).
   - Until these exist, M6 is built and accepted against the fake store on the live stack,
     and the sandbox run is done when the accounts are ready. Also needed: the naira price
     tier for each pack (questions #1).
7. **Do gifts count toward the daily spend cap (MN-9)?** The cap is M7, but the answer
   decides what `spent_today` counts. MN-9 only mentions paid filters switching off.
   **Recommendation:** `spent_today` counts all coin spending (gifts included), so the cap
   protects people from overspending; reaching it switches off paid filters only, and gifts
   stay allowed.
8. **Screens with no design:** the History tab, "Claimed today", the receiver's gift toast,
   the gift animation (a short scale-and-fade of the gift icon), and purchase errors
   (cancelled, pending, failed).
