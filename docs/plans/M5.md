# M5 — Friends and profile

**Goal (PRD):** screens 07 and 09, friend requests, saved chat history and push notifications.
Covers FR-14 (add friend during a call), FR-15, FR-16, FR-17 (push) and FR-19.
**Accept:** a friend request round-trip works, and a message to a friend whose app is closed
arrives as a push notification.

## Backend

**Friendships (FR-14, FR-16)**
- `Friendship` model, using the PRD fields (requester, addressee, status, created_at), unique
  per pair.
- `POST friends/requests {session_id}`:
  - Sends a request to the other person in a session. No user ids are ever exposed.
  - Allowed while the session is live and for **1 hour after it ends**, so "Add friend" works
    on the ended-chat screen too.
  - If both people request each other, the friendship is accepted at once.
- `POST friends/requests/{id}/accept | decline`. Declines are silent (the requester isn't
  told).
- Blocks still win (SF-5): blocking a friend ends the friendship, hides the chat and stops
  messages. Requests between blocked people are refused.

**Saved chat history (FR-15)**
- `Message` gets the PRD's `friendship` link (session or friendship).
- When a friendship is accepted, the messages from the session where they met move onto it.
  The 7-day stranger purge skips anything linked to a friendship.
- `GET friends`: friends with online state (presence ZSET), last message, unread count.
  Requests come back as a separate list. `GET chats/{friendship_id}/messages` is paginated
  (cursor, newest first).
- Websocket `chat.message` / `chat.seen` / `chat.typing` accept `chat_id` (friendship) as
  well as `session_id`. The same SF-8 filter, rate limit and FR-18 banner apply.
  `friend.request` and `friend.accepted` events go out (PRD).

**Friend calls (FR-16, see decision 1)**
- `call.invite {chat_id, mode}` creates a call session: a `MatchSession` with a new
  `friendship` link. That reuses rooms, tokens, the moderation agent, reports and blocks.
- The friend gets `call.incoming`, plus a push if their app is closed.
- They answer with `call.accept` or `call.decline`. After 30 s with no answer the call is
  missed, which adds a "Missed video call" line to the chat (a `system` message).
- An accepted call sends `match.found` to both, so the M3 call screens work unchanged.

**Profile (FR-19)**
- `GET/PATCH me/profile`:
  - `first_name`, `bio` (≤ 150), `city`, `languages` (fixed list: English, Pidgin, Yorùbá,
    Hausa, Igbo, French, Arabic), `interests` (≤ 5, from `GET interests`).
  - The 5-interest limit and the other rules are enforced in the service layer.
- `POST me/photos` (multipart), `DELETE me/photos/{id}`, and photo order through
  `PATCH me/profile`:
  - Up to 6 photos, in the private `photos` bucket, served through short-lived signed URLs.
  - **Every upload is scanned** by the moderation provider; nudity is rejected (SF-2
    applied to photos).
  - **The main photo must face-match the verified selfie** (FR-4 and the M1 decision),
    through `LivenessProvider.compare()`, which also gets a fake. A mismatch can still be
    added as photo 2–6.
- **Voice reveal (FR-13)** now sends both people's main photo (signed URL) in
  `reveal.accept`, finishing the M3 placeholder.

**Push (FR-17)**
- `DeviceToken` (PRD model); `POST me/devices {platform, fcm_token}` registers or refreshes
  one; tokens Firebase rejects are deleted.
- `PushProvider` interface: a fake (records pushes) and an FCM HTTP v1 implementation
  (service account in the environment).
- A push is sent when the recipient has **no open websocket**, for: friend messages, friend
  requests, accepted requests, and incoming friend calls.
- Content: see decision 3.

## App

- **07 Friends:**
  - Header with search, which filters friends on the device.
  - "ONLINE NOW" row of friends with the mint online dot.
  - Chats / "Requests · N" tabs.
  - Chat rows: initial or photo, name, time, last message, unread badge.
  - Request rows: "Wants to be friends · met on video", tap for Accept / Decline (sheet,
    no design).
- **Friend chat:** the Chat screen (06) in friend mode:
  - saved history with paging
  - Seen and typing
  - **voice and video call buttons** in the header (shown for friends only)
  - report and block
- **Incoming friend call:** a full-screen sheet ("Kwame is calling · Video") with Accept and
  Decline. No design.
- **09 Profile:**
  - The photo grid (main photo with the "Selfie verified" badge, add, remove, reorder by
    long-press).
  - First name, city, about-me (150 chars), the interests grid with "N of 5 picked" (extras
    disabled at 5), "I speak" chips with "+ Add", and Save.
  - The "Korram Plus" pill opens `/plus` (M7).
  - **Shown full screen, as in the design** (back button, no bottom bar); the Profile tab
    opens it.
- **Add friend comes back:**
  - the video-call control (FR-14), turning mint when sent
  - the "Add as friend" quick reply in stranger chat (M2 decision 5)
- **Push:**
  - `firebase_messaging` registers the token after sign-in and refreshes it.
  - Tapping a notification opens the friend chat, the Requests tab, or the incoming call.
  - Firebase only starts when you build with `--dart-define=PUSH=fcm` and the Firebase config
    files are present, so the app runs without them.

## Tests and acceptance

- **Backend:**
  - request round-trip, mutual auto-accept, decline, the 1 h window, blocked pairs refused
  - history moved on accept, and the purge skipping it
  - friends list with unread, last message and online
  - friend messages in real time
  - **push only when offline**
  - call invite, accept, decline and missed
  - profile limits (photos 6, bio 150, interests 5), photo scanning and face match
  - signed URLs, and reveal sending photos
- **Acceptance (live stack, e2e):**
  - Two app clients: A sends a request from a session, B accepts, both see `friend.accepted`,
    and the friendship appears in both `GET friends`.
  - B closes its connection; A sends a message; the push provider records a push to B's
    registered token with the right deep link.
  - With your Firebase project set up, the same test sends a real FCM message.
- **App:** widget tests for 07 (tabs, requests, search, unread), friend chat (history, call
  buttons), the incoming call sheet, 09 (limits, photo states, save), Add friend in a call,
  and push deep links. Golden images of 07 and 09 against the designs.

## Decisions to confirm

1. **Friend calls in M5.** FR-16 says friends can call each other directly, and the Inbox
   design shows "Missed video call". **Recommendation:** include the in-app version above
   (ringing sheet, push when closed, missed calls). Native call UI (CallKit / Android
   ConnectionService) would add a lot and isn't required by the PRD, so it waits until
   after the MVP.
2. **Profile is full screen,** as designed (back button and Save bar, no tab bar). The
   Profile tab opens it.
3. **What notifications show.** **Recommendation: no message text on the lock screen**
   ("Kwame sent you a message"), because chats can be personal and phones are shared.
   Showing a preview is a one-line change if you prefer it.
4. **Friend-request window:** during the conversation, or up to 1 hour after it ends.
5. **Photo rules:** every photo is nudity-scanned, and the main photo must match the
   verified selfie (from M1).
6. **Firebase.** Real pushes need a Firebase project (Android `google-services.json`, iOS
   `GoogleService-Info.plist` plus an APNs key) and a service-account key for the backend.
   Until you have them, pushes go to the fake and the app skips Firebase.
7. **Screens with no design:** the request Accept/Decline sheet, the incoming-call sheet,
   friend-chat call buttons (06 shows them, so this follows the design), the photo
   picker/crop and the language picker.

## Outcome (done 2026-10-20)

**Acceptance** (`make test-e2e`, live stack, fake push provider)
- **Friend request round-trip:** A sends a request from a video session, B gets
  `friend.request` live and accepts, both get `friend.accepted`, and each appears in the other's
  `GET friends` with the same chat.
- **Push to a closed app:** B registers a token and closes its connection; A's message produces
  a push to B's token, "Ada sent you a message", deep link `{type: chat, chat_id}`. The message
  text is not in the push (decision 3).
- **Friend call (extra):** A calls B, B gets `call.incoming`, answers, and both are connected
  with the friend chat attached, **161 ms** after the answer.
- A real FCM send still needs the Firebase project (questions #31).

**Tests:** backend 173, app 109 (+ goldens of 07 and 09 against the designs), console 5,
end-to-end 7/7. Release APK per CPU type: arm64 **32.2 MB** (was 31.7), armeabi-v7a 25.1 MB.

**Bug found on the way (fixed)**
- **Friend requests returned 500 on the live stack.** The `friend.request` event carried a
  `datetime`, which the Redis channel layer (msgpack) can't send. Unit tests didn't see it
  because they record events instead of sending them. Now every event is converted to plain
  JSON in one place (`core.realtime.json_safe`, full-precision times), and the test fixture
  records exactly that, so a payload the real layer can't carry fails in unit tests too.

**Changes beyond the plan**
- **Report from a friend chat** (app-store rule): `POST reports` takes `chat_id` instead of
  `session_id`; the evidence is the friend chat's last 200 messages. After reporting, the
  sheet offers "Back to friends".
- An app clock provider, so Home's greeting and the chat times are stable in goldens.
- The bio counter is hidden (09 shows none); the 150 limit is still enforced.

**Different from the plan**
- **Photo order:** tap a photo for "Make main photo" / "Remove" instead of long-press drag. The
  server takes any order (`photo_order`), so drag can come later without API changes.
- **No crop step:** the gallery picker only; the server re-encodes to ≤ 1080 px and strips
  EXIF.

**Not done / to verify**
- Real FCM (needs the Firebase project and config files, questions #31).
- `firebase_messaging` 17 deprecates registration tokens (`getToken`) in favour of
  installation IDs. We still use tokens because FCM v1 sends to them; moving needs the backend
  to switch too.
- Native call UI (CallKit / ConnectionService), after the MVP (decision 1). An incoming call
  while the app is closed arrives as a normal notification.
- No phone run of the new screens (widget tests and goldens only).
