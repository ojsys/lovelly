# M1 — Onboarding

**Goal (PRD):** screens 01, 14, 15, 16, 17. Send the code through an SMS provider, the age
gate, the selfie liveness check (behind a swappable provider interface), and permissions.
**Accept:** a new phone number gets from install to verified on a real device, an under-18
date of birth is blocked, and a third failed selfie goes to manual review.

Decisions already made (questions.md #8–10, #13): the UI says **Korram**; a new phone-entry
step is added; "get a call instead" is built; the selfie is the face reference.

## Flow

```
Welcome ─► Phone ─► Code (14) ─► Basics (15) ─► Selfie (16) ─► Permissions (17) ─► Home
   │        └──── step 1 of 4 ───┘   step 2        step 3         step 4
   └─ Google / Apple ─► (FR-2: still needs a verified phone) ─► Phone ─► …
```

The server decides the next step. `GET me/verification` returns `next_step`, and a go_router
redirect sends the user there. Killing the app mid-onboarding resumes at the right screen.

## Backend

**Models** (`accounts`):
- `Profile`, with the PRD fields. M1 only writes `first_name`, `is_verified` and
  `verified_at`.
- `Verification`, with the PRD fields: kind `otp` / `selfie` / `manual`, status, score,
  attempts, reviewer. One row per attempt.
- `SocialAccount` (provider, subject, user). This is needed for FR-2 and isn't in the PRD
  data model. `User.phone` becomes nullable, because a Google/Apple user has no phone until
  verified. It stays unique.
- `DeniedPhone` (a hash of the phone, reason, created_at). FR-3 needs a deny list, which isn't
  in the PRD data model. Storing the hash means we don't keep minors' numbers.
- Selfie images are stored in the private `photos` bucket under `selfies/`. Profile photos
  come in M5.

**Endpoints** (`/api/v1/`):

| Endpoint | Behaviour |
|---|---|
| `POST auth/otp/request` `{phone, channel: sms\|voice}` | Normalise to E.164 (+234 by default). Reject a denied phone. **FR-1:** a 6-digit code, hashed in Redis with a 5 min TTL, at most 3 per hour per phone across both channels, and a 60 s resend gap. Sending goes through `SMSProvider.send_code(phone, code, channel)`. |
| `POST auth/otp/verify` `{phone, code}` | Allows 5 wrong tries per code, then the code is burned. On success it gets or creates the user (one account per phone), links the social account if signed in that way, and returns a JWT pair and `next_step`. |
| `POST auth/social` `{provider, id_token}` | Checks the Google/Apple ID token through an `IdentityProvider` interface (real check against Google's and Apple's public keys, plus a fake). Returns a JWT pair. `next_step` is `phone` until a phone is verified (FR-2). |
| `POST auth/refresh` | SimpleJWT. Access 15 min, refresh 30 days. |
| `PUT me/basics` `{first_name, dob, gender, adult_confirmed}` | **FR-3:** an age under 18 (from date of birth, UTC) bans the account, adds the phone to the deny list, blacklists its tokens, and returns 403 `underage`. The date of birth is never sent back out; only `age` is. |
| `POST me/selfie` (multipart `pose_front`, `pose_left`) | **FR-4:** `LivenessProvider.check()`. A pass stores the reference and sets `is_verified` if phone and basics are done. A fail increments attempts. The 3rd fail creates a `manual` Verification with status `pending` and returns `manual_review`. **SF-3:** an estimated age under 18 suspends the account and sends it to manual review. |
| `GET me/verification` | `{phone_verified, basics_done, selfie: none\|passed\|failed\|manual_review, attempts_left, is_verified, next_step}` |

- **SF-1:** an `IsVerified` permission class, used by every matching endpoint from M2 on.
- Throttling on auth endpoints per IP and per phone, through a Redis cache (NFR rate limits).
- Manual review in M1 means approve/reject actions in Django admin. It moves to the moderator
  console in M4.
- **Providers:** `SMSProvider` gains `channel` (sms or voice). In dev the fake logs the code to
  the API logs, so the real-device test works without an SMS account. A real SMS adapter needs
  your provider choice (see below). `LivenessProvider` stays fake. Env
  `FAKE_LIVENESS=pass|fail|underage` drives the acceptance tests.
- **Tests** named by requirement ID, for example `test_fr1_fourth_code_in_an_hour_is_refused`,
  `test_fr3_under_18_is_banned_and_phone_denied`, and
  `test_fr4_third_failed_selfie_goes_to_manual_review`.

## App

- **Packages:** `camera` (live front camera for the selfie), `permission_handler`,
  `flutter_secure_storage` (tokens), `google_sign_in`, `sign_in_with_apple`.
- **Generated Dart client:** `swagger_parser` builds dio clients and models from
  `/api/v1/schema/` (pure Dart, no Java needed). The script is `app/tool/gen_api.sh`. Riverpod
  repositories wrap the client, and a dio interceptor attaches and refreshes tokens.
- **Shared `OnboardingScaffold`:** 44 px round back button and the 4-segment step bar
  (coral / `#26242F`, 6 px, gap 6). Padding is 52/24/32, from the designs.
- **Screens:**
  - **01 Welcome:** wordmark becomes "korram". Google and Apple buttons are wired up. Terms
    and Guidelines links open the published URLs (needed, see below).
  - **Phone (new, no design):** step 1. Title "What's your number?", a field with a fixed +234
    prefix and a numeric keypad, and Continue. Built from Verify's components.
  - **14 Verify:** a 72 px code field with 18 px tracking. The border turns mint when 6 digits
    are in. Supports SMS autofill (`one-time-code`). "Sent to +234 803 ••• ••42 · Change
    number". A 60 s "Resend code in 0:42" countdown, then "Resend code". "get a call instead"
    sends a voice code. Verify is disabled until 6 digits are entered. Errors show inline:
    wrong code, expired, too many codes.
  - **15 Basics:** first name; day/month/year fields with validation; Woman/Man/Other
    toggles; the 18+ checkbox. Continue is disabled until everything is valid and the box is
    ticked.
  - **16 Selfie:** live camera preview clipped to the 260×330 oval. The ring is coral for the
    front pose, gold for the left turn and mint when done, matching the design. Labels are
    "Take selfie" and then "Capture". When done: "You're verified", the mint check badge, and
    "Verified in N seconds".
  - **17 Permissions:** Camera, Microphone and Notifications rows, each with Allow/Allowed
    buttons that trigger the OS prompts. "Start meeting people" is enabled only when camera
    and mic are both allowed. "Text chat only for now" goes on in text-only mode (FR-5). A
    permanently denied permission shows "Open settings".
- **States with no design.** These are built from the tokens and existing components, and are
  listed so you can review them:
  - The phone step.
  - The under-18 "Account removed" screen.
  - Selfie failed, with attempts left.
  - Selfie in manual review ("We're checking your selfie"). The app holds the user there until
    the review is done.
  - The OTP error messages.
- **Tests:** widget tests for each screen, including the disabled/enabled rules, the
  countdown, the attempts-left copy and the text-only path; golden images of each screen in
  its design state; and repository tests against a mocked API.

## Acceptance demo

1. **Android emulator, fake SMS:** enter a new number, read the code from the API logs, then
   do basics, selfie (emulator camera) and permissions, ending on the Home placeholder as
   verified.
2. **Real device:** the same flow on your phone. It needs your phone and the dev API on the
   same network, or a tunnel.
3. A date of birth under 18 shows "Account removed". Requesting a code for that number again
   is refused.
4. With `FAKE_LIVENESS=fail`, the third selfie attempt shows the manual-review state, and the
   row appears in Django admin.

## Decisions to confirm

1. **Selfie privacy vs "selfie as reference".** The privacy rule says to delete raw selfie
   images 30 days after a pass, and the Selfie screen says the selfie is "never shown to other
   people". So the selfie stays **private**: it is never displayed and is used only to
   face-match the main photo the user adds in Profile (M5). After 30 days the raw images are
   deleted, and later photo changes are matched against a face template stored by the
   liveness provider. If the chosen provider can't store templates, a photo change after 30
   days triggers a new selfie. OK?
2. **Matching before a profile photo exists.** Voice calls show a blurred photo (FR-13). Until
   M5, verified users have no public photo, so the app shows an initial avatar, as in the
   Home and Chat designs ("AO", "K").
3. **SMS provider (questions.md #4).** M1 ships with the fake (codes in logs). For real
   texts, pick one: **Termii** (Nigerian, supports SMS and voice codes, DND-route numbers),
   **Twilio Verify**, or **Africa's Talking**. I'd suggest Termii. I need an account and API key
   to build and test that adapter.
4. **Google / Apple sign-in setup.** I can build both, but testing on a device needs a
   Google OAuth client (Android SHA-1 and iOS client ID) and an Apple Developer team with
   Sign in with Apple enabled. If you don't have those yet, the buttons ship wired but
   disabled behind a config flag.
5. **Terms and Community Guidelines URLs.** Welcome and Basics link to them, and the store
   rules require them. Placeholder URLs until you have real ones?
6. **Resend timer** is 60 s, per the PRD (questions.md #11).

## Outcome (done 2026-10-19)

Acceptance, against the Docker stack with fake providers:
- **New number → verified:** `app/test/e2e/onboarding_e2e_test.dart` drives the app's real
  session controller, repository, generated client and auth interceptor against the live API
  (phone → code from the logs → basics → selfie upload to MinIO → permissions → done). It also
  checks a silent token refresh.
- **Under 18 blocked:** same e2e file. The account is banned, tokens revoked, and the number
  is refused on the next request.
- **Third failed selfie → manual review:** run live with `FAKE_LIVENESS=fail`. Attempts 1–2
  fail, the 3rd creates a pending `manual` Verification (visible in Django admin), and the 4th
  is refused.
- **Not done: a run on a real phone or the emulator UI.** The Android emulator on this machine
  was too starved for memory and CPU to drive (2m26s to first frame). The screens are covered
  by widget tests and golden images compared against the designs. A run on your phone is
  still needed.

Decisions taken while building:
- Decision 1 above (the selfie stays private) was accepted along with the placeholders.
- The 60 s resend gap is **per channel**, so "get a call instead" works during the text
  countdown, as the design shows. The 3-per-hour limit covers both channels.
- The API accepts JSON only, except the multipart selfie upload. The OpenAPI schema uses
  separate request and response components, and CI fails if `app/api/openapi.yaml` drifts.
- Toolchain pins: `retrofit` 4.9.0 + `retrofit_generator` 10.1.4 (newer pairs don't compile
  together), `permission_handler` 12 (13 needs a newer Android Gradle setup), and compileSdk 36
  (`flutter_secure_storage`).
- Back from Basics signs out (the phone stays verified); Selfie can go back to Basics;
  Permissions has no back button, because the selfie is already verified.
